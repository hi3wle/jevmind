## Grounded plan and challenge

Give the separately authorized Claude planner the original goal, acceptance criteria, protected constraints, relevant source/diff identity, known checks and material technical question. Use this prompt:

> Inspect the supplied repository evidence and propose the smallest feasible solution. Cite relevant files, symbols, contracts and conventions; distinguish observations from assumptions. State material decisions and unresolved requirements, steps and regression/verification strategy. Do not write production code/tests, launch workers or execute repository code. Ask for missing business rules rather than guess. Accept evidence-backed Codex challenges and revise material decisions only. Return one plan for the existing AI DevKit planning artifact.

Maintain one plan in that existing artifact, preserving its backlog. Record task/baseline, goal/criteria, source references, constraints, steps, material assumptions/decisions and verification strategy. Bind each challenge to the exact plan revision using a Git revision or trusted content identifier retained in the handoff; keep prior challenge references without creating a parallel plan. Record actual planner session/model and source identity when observed. Re-ground if source changes invalidate the plan.

The Codex worker that will implement performs the challenge in its current session:

> Read the original requirement, applicable policy and exact proposed plan revision. Inspect current source and verify material file/symbol/API references, contracts, feasibility, simplicity and testability. Treat the plan as a proposal. Return accept, revise or blocked with planRevision and findings containing location, concrete evidence, impact and proposed resolution. Resolve minor local implementation details yourself. After accept, continue implementation and verification in this same session; do not start another worker.

Check that the response matches the current plan/source and its status agrees with the findings. `accept` means no unresolved material objection; record minor adjustments locally and proceed. `revise` requires a concrete material design conflict with evidence, sent to the planner for one additional material revision by default, then challenged again by the same worker. Extend only with new evidence and explicit budget authorization. `blocked` covers missing authority/requirements or an unresolved material conflict; escalate the actual decision to the developer. Do not implement a materially disputed plan or turn routine local choices into approval requests.

## Implementation, review and recovery

After acceptance, the same Codex worker implements, runs affected checks on current source and handles confirmed corrections. Preserve mandatory project ownership rules. This runtime continuity is distinct from this harness repository's development-only implementer → unit_tester → code_reviewer workflow; it does not authorize those roles for a target task or override its policy. If target policy prevents same-worker continuity, resolve that conflict before proceeding and do not claim Mode C acceptance.

For final review use [harness-review](../harness-review/SKILL.md): a fresh Claude reviewer session, separate from planner/worker, receives original criteria, neutral constraints, verified snapshot/diff and current check evidence. The reviewer must actually read an approved native/CI test-result artifact or approved verbatim output carrying command, exit status and source/snapshot binding; a parent summary alone is insufficient. A neutral trusted runner may hold only approved test-evidence files, with no target instructions or plugins. Missing required evidence leaves `insufficient_evidence` unless a validated blocker requires `changes_required`. Do not send planner/worker transcripts by default. Its snapshot/status invariants and R0 → F1 → R1 limit apply. The same Codex worker handles F1; the single correction budget is consumed when F1 starts. Refresh affected checks/snapshot for R1. Remaining blockers, unavailable R1 or insufficient evidence leave the required gate open; another correction needs explicit authorization and budget. Human review remains separate.

At handoff retain exact worker session ID/cwd, plan revision, challenge, source/check/review references, revision/correction budgets consumed and next action in the existing planning/testing records. On disconnect/quota exhaustion preserve work and establish worker liveness/ownership before retrying; unknown liveness means no duplicate launch. Resume the exact worker through a supported native interface, re-read original requirements/rules/plan/current source and reconcile external edits before writing; invalidate affected stale checks/review. If resume is unavailable, preserve a manual handoff and report continuity unverified rather than silently creating a replacement worker. Report all gates using AGENTS.md completion precedence; local artifacts alone never satisfy N3 or prove Mode C value.
